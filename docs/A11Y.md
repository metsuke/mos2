## Propósito

Definir la accesibilidad de MetsuOS como **obligatoria**.

La interfaz actual es MOSh (línea de comandos) más los scripts de lanzamiento e instalación. No hay GUI. Este documento adapta WCAG 2.2 y, donde encaja, EN 301 549 e ISO 9241-171 a ese contexto. No afirma conformidad de sitio web.

---

## Precedencia

1. No excluir los perfiles de discapacidad declarados en este documento.
2. Seguridad (SEC) y normas de sistema (SSS).
3. Resto de specs y código.

Si A11Y y SEC chocan:

- Prevalece A11Y para no dejar fuera un perfil soportado.
- No se recorta SEC en silencio.
- Se escribe el debate: riesgo, mitigación, dónde vive la excepción (SEC + este archivo + SRelD).

Muchos supuestos conflictos no lo son. Rechazar `import requests` no impide usar un lector de terminal. Un conflicto real sería un mensaje incomprensible “por no filtrar datos” frente a un mensaje accionable.

## Referencias (adaptación, no sello)

| Fuente | Uso en MetsuOS |
|--------|----------------|
| WCAG 2.2 Perceptible | Texto plano; no basar el significado solo en color o en ANSI |
| WCAG 2.2 Operable | Todo por teclado; help, man, exit predecibles |
| WCAG 2.2 Comprensible | Español consistente; help() no vacío; errores con siguiente acción |
| WCAG 2.2 Robusto | Prefijos estables; salida estructurada en líneas |
| EN 301 549 / ISO 9241-171 | Software interactivo y CLI: mensajes, teclado, no solo-color |

Nivel de ambición: equivalencia **AA adaptada a CLI**.

## Perfiles soportados

| Perfil | Qué debe cumplir el sistema | Qué no aplica aún |
|--------|-----------------------------|-------------------|
| Solo teclado | MOSh y scripts se usan sin ratón | Atajos de GUI |
| Lector de pantalla de terminal | Mensajes en texto; prefijos; sin información solo en color | APIs de lectores de escritorio |
| Baja visión | No depender de contraste de color del terminal | Temas visuales propios |
| Daltonismo | Color no es la única señal | Paletas de un TUI gráfico |
| Carga cognitiva | help/man; un comando = un contrato; errores con pista | Tutoriales multimedia |
| Sordera / sin audio | El producto no usa sonido | N/A explícito |

Un perfil no listado aquí no está “cubierto” hasta que se añada con requisito y verificación.

## Requisitos operativos (resumen)

La numeración formal vive en el SRS (`REQ-A11Y-*`). Aquí la política:

- Todo comando de sistema o usuario tiene `help()` que devuelve texto no vacío.
- Los comandos de sistema tienen página en `docs/man/` cuando se añaden.
- Los mensajes de error y de seguridad llevan un prefijo estable (por ejemplo `[SEGURIDAD]` o `Error:`).
- El texto dice qué ha pasado y qué puede hacer la persona (comando, documento o ruta relativa).
- Los scripts `mos2.sh` e `install.sh` fallan con texto guiado, no con un código mudo.
- No se usa solo color ANSI para distinguir ok / error / aviso.
- El arranque que bloquea por tests explica que no hay sesión y cómo lanzar pytest.

## Cómo se registra un conflicto A11Y ↔ SEC

1. Describir el perfil afectado y el control de seguridad.
2. Alternativas (mensaje más claro, mismo rechazo; no desactivar el control).
3. Decisión.
4. Anotar en SEC, en este archivo (sección de excepciones) y en SRelD si cambia la baseline.

### Excepciones vigentes

Ninguna. El rechazo de imports ilegales se mantiene; el mensaje debe ser comprensible.

## Verificación

- Tests automáticos donde sea posible (help no vacío, prefijos, pista en fallos de arranque).
- Inspección de scripts y de help/man.
- No se exige laboratorio de lectores de pantalla en esta baseline; sí se exige que la salida sea texto lineal.

Detalle: docs/specs/06-TEST-Verification-and-Validation.md (se actualizará en el paso 1.5).
