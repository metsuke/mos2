## Frente A — infraestructura de apps (no la suite)

### Instalar

No basta el path local.

| Origen | 07 completa |
|--------|-------------|
| Path local | sí (`apps/foo` = relativo a la **raíz del clone**) |
| Repositorio git | sí (clonar/actualizar a un cache y luego el mismo ciclo de validación) |

Destino según **configuración de la app** (campo estable, p. ej. `ambito` o `acceso` ampliado):

| Destino | Dónde | Significado |
|---------|--------|-------------|
| usuario | `.mos/apps/<id>/` | Solo ese usuario; se puede quitar sin tocar el sistema |
| sistema | almacén de sistema del clone (p. ej. `rootfs/opt/apps/<id>/`) | Visible para el sistema; gana a las de usuario en el nombre |

Misma estructura interna (`app.json`, `commands/`, `minimoslib/`, `man/`).  
El sistema las trata distinto: prioridad, quién las borra, tests de arranque (las de sistema cuentan siempre).

### mini-moslib y SEC

- Comandos: `from minimoslib.x import …` si el módulo está en **esa** app.
- Prohibido: `apps.dev.commands`, otra app, libs ajenas.
- Loader: un minimoslib por app, sin mezclar.

### Prefijos de invocación (como `user_`)

Ejemplo: comando `app_dev_paso`.

Se puede llamar:

- `app_dev_paso` (nombre completo)
- `dev_paso` (sin el prefijo `app_`)
- `paso` (nombre corto)

Si hay colisión, gana el de **más prioridad**. No se pisa en silencio: el de abajo no se ejecuta.

| Prioridad (alta → baja) | Origen |
|-------------------------|--------|
| 1 | Comando de sistema (`moslib/commands`) |
| 2 | App **de sistema** |
| 3 | App **de usuario** |
| 4 | Comando `user_*` |

El loader resuelve igual que con `user_`: prueba el nombre pedido; si no hay sistema, busca formas largas/cortas en apps sistema, luego apps usuario, luego `user_`.

`help` indica de dónde salió (sistema / app-sistema / app-usuario / usuario).

### Help y man

`man` de un comando de app lee el man **de esa app**, no `docs/man` del núcleo.
